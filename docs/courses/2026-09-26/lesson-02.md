# 第二堂｜octoscode × Octoscript：和 Agent 一起做应用

9/26 14:00–16:00，北京时间，120 分钟（含 10 分钟休息）。延续上午的参会天气卡。重点是人与 Agent 的协作机制，不教授脚本语法或底层源码。

## 学习结果

学员能把任务、上下文、边界与完成证据交给 octoscode 中的 Agent；能理解 Octoscript 卡片的结构、数据和状态；完成一次小改动、一次运行检查和一次反馈修正。开发协作与应用运行各有自己的会话和授权，不假设上下文自动互通。

## 讲稿与操作提示

### 14:00｜让目标足够小，结果足够明确

选取一个改动：“服务取不到数据时，界面清楚说明当前不可用，保留城市信息，不呈现编造的天气。”也可改善信息顺序或既有温度单位操作的提示，但每组只选一个。

讲述：“今天不要求大家从零造整个天气服务。我们先练会一个完整循环，之后就能把同样的方法用于自己的参赛作品。”记录基线版本和改动前表现，避免最后无法判断改进来自哪里。

### 14:10｜octoscode 提供协作入口，Octos 执行任务

展示真实 octoscode 会话，把 [练习包中的任务指令](workbook.md#给-octoscode-的首轮指令) 交给 Agent。让 Agent 先指出将读取哪些文件、怎样验证，再进入修改。观察它是否使用锁定版本的参考材料。

讲述：“你负责目标、边界和验收。Agent 可以读材料、修改、运行和整理证据，但它说‘完成’时，我们仍要看实际结果。”解释内环执行、外环复核的分工，正式 OctoLoop 内容留给次日。

说明模型、工具与会话由内核提供；终端是协作界面。mock 模式适合展示终端布局，不能作为真实模型完成任务的证据。不要向学员承诺命令行启动提示等于无人值守后台运行。

### 14:25｜用五张标签解释 Octoscript

打开准备好的卡片，只标出“结构”“数据来源”“状态”“事件”“文字”，不逐行讲语法。让学员把城市、温度、单位切换、等待提示归入对应位置。

讲述：“这个练习使用 Octoscript 的 UI L0 表达。它约束卡片可以描述什么，由宿主提供数据与真实控件。写出一个服务名称，不等于已经获得该服务或用户授权。”说明工作流能力授权是另一个相关机制，不把工作流 CLI 当成卡片渲染器。

强调三次检查的不同问题：源码是否可接受；宿主能否正确运行；用户是否完成任务。普通 `octoscript check` 面向工作流语法，本课 UI 卡片应使用匹配版本的 UI L0 路径和宿主验证。课堂只展示检查结果，不讲校验器实现。

### 14:40｜演示三：一轮修改

按 [演示 B](demo-runbook.md#演示-b开发-agent-修改卡片) 操作。先展示原版，再让 Agent 修改练习副本中的一种状态。只展示关键差异和验证结论，不让终端长输出主导讲课。

让学员做一次“验收者”：如果新提示在失败时根本没出现，指出证据缺失；如果 Agent 使用固定数值，要求区分练习数据与线上数据；如果没有真实点击记录，不接受“按钮正常”的结论。

然后在 OctoSense / AppCard 中运行修改版，执行同样的动作。保留前后版本、运行入口与失败提示截图。无法运行时进入备用练习并记录阻塞，不能用静态设计图充当运行结果。

### 15:10｜25 分钟协作练习

前 5 分钟检查任务和允许改动范围；接着 10 分钟由 Agent 完成一个改动；5 分钟运行正常与失败场景；最后 5 分钟由同伴复核并填写证据。产品与设计同学可负责需求、操作与验收，开发同学负责环境，不按代码量分配成绩。

助教优先解决任务过大、参考版本错用、模型不可达和无法启动四类阻塞。课堂不升级运行时，不从零安装整套 Rust 工具链。进展较快的小组可检查窄窗口或第二个城市，不追加新的服务接入。

### 15:35｜演示四：有证据地退回修改

使用事先准备、明确标为“故障练习”的案例：界面显示“数据已更新”，实际数据没有成功刷新。请学员写反馈，而非只说“不好用”。按“复现步骤 → 预期 → 实际 → 证据 → 允许修改范围”提交给 Agent。

讲述：“好的反馈能让下一轮更接近完成。外环要检查目标是否达成，不能只重复内环的完成报告。”修正后重新执行原失败动作，并确认正常路径仍可用。

可用本次备课内环作为旁例：octoscode 完成了 Octoscript 文档事实整理；主讲人仍需对照源码，纠正局部检索结论和不同 profile 的混用。不要展示模型账号、配置或会话隐私。

### 15:50｜交付一个能继续做的作品

每组提交任务说明、修改文件、正常/失败两张截图、复现步骤和已知限制；附一句“Agent 做了什么、人检查了什么”。有条件再录 60–90 秒演示：任务 15 秒、操作 30 秒、结果与失败处理 30 秒、限制 15 秒。

回到比赛：最佳 Agentic 关注任务自动化和可核验结果；技术突破在应用价值基础上，进一步说明对生态或 OctoSense ROM 的贡献。运行时稳定接入、可复用能力适配和清晰的失败传播可以成为后续方向，需真实实现并验证后参评。

作业延续自己的参赛作品，不额外造第二个项目。9/28–10/4 的制作周用于完成真实任务与材料，具体提交要求沿用正式赛事安排。
