# 学员练习包｜同一个任务，完成一次可核验的迭代

配合 [第一堂](lesson-01.md) 与 [第二堂](lesson-02.md)。将下面模板复制到自己的练习目录。使用讲师准备并验证过的卡片副本；不直接修改运行时依赖和公共参考文件。

## 上午：任务说明（20 分钟）

```text
作品名：参会天气卡 / 我的选题
用户与场景：谁，在什么时候，遇到什么问题？
一句话意图：
需要的输入：城市、目标日期、单位……
数据来源：真实服务 / 明确标注的练习数据
Agent 负责：理解任务、组织信息、调用已提供的能力……
用户负责：确定目标、批准有影响的操作、判断结果……
一个必要操作：
操作后的可观察结果：
等待时显示：
没有数据或执行失败时显示：
本次不包含的功能：
完成证据：具体动作、结果、来源、时间、截图或日志
```

天气示例的验收条件：城市与请求一致；预报日期对应用户要求；数值来自数据源；切换单位后数值与标签一致；获取失败时明确显示不可用。来源与时间至少记录在验收材料中，是否显示在界面取决于本次改动范围。空气质量若未取到数据，不填虚构值，也不把温度服务的成功当作空气质量成功。

同伴互审：哪一条无法通过操作或证据判断？把它改写清楚。将一个上午发现的问题收敛为下午的唯一改动。

## 给 octoscode 的首轮指令

将方括号替换为自己的路径和任务。先让 Agent 读取讲师提供的环境说明；引用卡片的 UI L0 示例，不混用工作流示例。

```text
你协助我完成黑客松参会天气卡的一次迭代。

任务说明：[粘贴上午的一页说明]
本轮只改：[例如：数据获取失败时的文案与信息优先级]
工作目录：[练习副本绝对路径]
可修改文件：[明确列出本组的卡片及说明文件]
只读参考：[匹配课堂锁定版本的 weather.card、UI L0 文档、运行说明]
启动与检查入口：[讲师预演通过的命令或操作步骤]

先确认当前文件和版本，复述你的理解、准备修改的位置和验证方法。
然后完成这一个改动，保留正常路径，并核验实际运行结果。
不要升级依赖、重构整个宿主或扩大任务范围。
不要读取个人账号资料、把凭据写入作品，或代我发送外部消息。
实时数值必须来自服务；练习数据要标注。失败与未知必须如实呈现。
不要用普通工作流 check 的成功代替 UI L0 / 宿主检查。
如没有执行界面的工具，就写出需要我操作的步骤，等待真实反馈。

交付：改动摘要、实际执行的验证与结果、未执行项、复现步骤、已知限制。
```

任务较复杂时，先请求 Agent 分成能独立验收的小步，由人选择第一步。不要一次要求“邮件、地图、支付、聊天全部接好”。

## 下午：25 分钟练习

| 用时 | 做什么 | 留下什么 |
|---|---|---|
| 5 分钟 | 给出任务、核对参考版本与允许改动范围 | Agent 复述和计划 |
| 10 分钟 | 完成一个改动，检查差异 | 修改后的卡片副本与变更说明 |
| 5 分钟 | 运行正常与失败路径，执行真实操作 | 操作记录和两张截图 |
| 5 分钟 | 同伴复核，决定通过或退回 | 验收表与下一步 |

没有环境的小组结对使用一台已配置机器；仍无法运行时完成任务/审查练习，并标注“未完成运行验证”。静态图、操作脚本和预期结果不能填入“实际结果”。

## 退回 Agent 的反馈模板

```text
本轮未通过的验收条件：
复现环境与版本：
复现步骤：1. … 2. … 3. …
预期结果：
实际结果：
证据文件与时间：
允许修改范围：
修复后必须重测：原失败步骤 + 原正常操作
请先说明可能原因与核验方式；不要因一次失败升级全部依赖。
```

示例：“关闭测试数据源后，卡片仍显示‘已更新’，没有失败提示。预期显示无法获取并保持城市可见。证据为 error.png 与对应日志时间。请检查现有失败分支，并在恢复数据后重测正常单位切换。”故障只在隔离的演示数据源中制造；不影响公共服务或他人的会话。

## 一页验收记录

| 检查项 | 实际动作和结果 | 证据 | 状态 |
|---|---|---|---|
| 意图与结果一致 | 待填写 | 待填写 | 待测 |
| 数据来源、城市与日期可核对 | 待填写 | 待填写 | 待测 |
| 一个真实操作改变正确状态 | 待填写 | 待填写 | 待测 |
| 等待与失败能被理解 | 待填写 | 待填写 | 待测 |
| 这次改动没有破坏正常路径 | 待填写 | 待填写 | 待测 |
| 第二人可按说明复现 | 待填写 | 待填写 | 待测 |

状态填“通过 / 未通过 / 未测”，不要把“可能通过”写成通过。

建议交付目录：

```text
my-entry/
  task.md             # 任务与完成条件
  app/                # 本组卡片或应用源码
  changes.md          # Agent 修改了什么，人检查了什么
  run.md              # 版本、启动方式、数据依赖、复现步骤
  evidence/
    normal.png        # 实际正常操作后的结果
    failure.png       # 失败或无数据时的实际界面
    checks.md         # 日期、环境、动作、结果、未执行项
  limitations.md      # 已知限制与后续工作
```

截图中不出现 API Key、个人邮件、账号或访问令牌。预录回放注明录制版本与时间；不同版本的证据分开存放。课程练习材料可继续扩展成参赛作品，正式提交格式与规则以官网为准。

## 课后迁移到自己的场景

- 邮件：从“整理回复草稿”开始，分别验证读取、草稿、用户确认与发送；未接通发送时只交付草稿能力。
- 日历：先确认日期、时区和冲突，再考虑写入；演示与真实日历数据明确区分。
- 即时消息：使用 Rinx 的宿主与授权机制，将结果关联到具体会话；消息能力不是网页卡片自带权限。
- 技术突破：选取一个阻碍真实任务的宿主或系统问题，保留修改前后的任务证据，再整理可复现贡献。
