## 课程目标与边界

选手负责提出真实目标、限定操作范围和判断结果，Agent 协助完成需求梳理、应用制作、试用改进、验证与演示。课程重点是“这些项目做什么、彼此如何配合、如何让 Agent 帮我参赛”，采用准备好的环境和可观察的应用演示。

本届以 [hagency-org/Rinx 小程序宿主](https://github.com/hagency-org/Rinx) 为主要开发基线，沿用聊天、联系人与发现界面。该版本已支持网页小程序卡片与原生 Octoscript 文章编辑器：打开应用、独立授权、保存草稿、原生预览、分享应用和确认发送。9/26 的机制课另使用 OctoSense / AppCard 天气卡，两个宿主的能力与授权分别验证。当前 Rinx 原生示例仅接受内置编辑器，新增原生应用需扩展并构建宿主；网页卡片不自动获得聊天或账号能力。具体起步方式和已验证范围见 [小程序基线说明](rinx-miniapps.md)。八个项目按选题组合，hagency 用于软件协作，不要求全部接入。

最佳 Agentic 奖评价应用完成真实任务的自动化能力；最佳技术突破奖在可运行 Agentic 应用的基础上评价生态反哺和 OctoSense ROM / 系统突破，不要求先获得最佳 Agentic 奖。课程讲清改进的价值和验证方法，不要求选手掌握底层实现后才参赛。

已公开获奖奖池保持 **¥50,000**，含现金奖金与 MiniMax Token 额度：一等奖 1 名 ¥20,000、二等奖 2 名各 ¥9,000、三等奖 3 名各 ¥4,000，均以团队（含单人队伍）为单位。两类新奖项与这 6 个金额名额的对应关系、能否兼得，以及现场邀请的综合排名办法待正式规则确定；不预设额外奖金或将其改成无奖金荣誉。另提供 MiniMax API 额度和 Kimi 编程权益用于开发，领取方式和使用期限随发放说明公布。

## 八个项目各自负责什么

| 项目 | 要理解的机制 | 选手如何借助它完成比赛 |
|---|---|---|
| OctoSense | 面向用户的 Agentic 应用入口，连接状态、操作和结果 | 从邮件、日历、天气等场景确定任务，检查应用是否真正完成事情 |
| Makepad | 原生应用界面的呈现与交互基础 | 向 Agent 说明信息、操作与反馈，观察运行界面并提出改进 |
| octoscode | 终端中的编码协作客户端 | 给 Agent 任务和上下文，查看生成、运行与修改结果，持续反馈 |
| Octoscript | 受约束的卡片表达与能力机制，区分 UI L0 与工作流 | 让 Agent 按宿主支持的表达生成与修改应用，并通过运行验证 |
| octos | Agent 运行内核，组织上下文、工具和任务执行 | 理解 Agent 如何获得信息、采取行动、报告进展与结果 |
| OctoLoop | octoscode 中的产品化双环 skill：内环执行，外环计划、观察和独立审查 | 把“执行任务”和“判断完成”分开；人确定目标、批准范围并最终验收 |
| Rinx | Rinx 是本届主要小程序宿主，沿用会话、联系人与发现入口 | 从原生文章编辑器学习分享、接收者授权、草稿隔离与确认发送，再扩展自己的场景 |
| hagency | 软件工厂中的任务组织与多 Agent 协作 | 分配任务、查看阻塞、核对证据并确认交付；作为即时消息下的软件协作示例 |

OctoLoop 的课程依据为 octoscode 仓库中的 [skill 定义](https://github.com/octos-org/octoscode/blob/main/.claude/skills/octoloop/SKILL.md) 与 [使用指南](https://github.com/octos-org/octoscode/blob/main/docs/OCTOLOOP_GUIDE.md)。它是双环协作的产品化入口：外环可以退回不符合目标的结果，内环继续执行；人负责审批和最终判断。

## 一条贯穿课程的选手与 Agent 工作流程

1. **选定一个真实任务。** 从 [OctoSense 官方 12 个场景](https://octosense.org/cn/#apps) 选择邮件、即时消息、日历、天气、新闻、音乐、视频、财经、导航、购物与物流、写作与创作、系统与设备中的主场景。写清用户遇到什么问题、输入来自哪里、什么结果才算完成。
2. **把目标交给 Agent。** 在准备好的 octoscode 环境中说明目标、可用项目、参考画面、可操作范围与完成标准。让 Agent 先复述任务和计划；选手检查是否理解正确。
3. **做出第一版并亲自使用。** 观察 Agent 使用上下文和工具推进任务，让其借助 Octoscript 与 Makepad 表达应用，并在公布支持的环境中运行。选手实际操作一次，记录状态、授权、执行反馈和结果。
4. **让执行与审查分别发生。** 用 OctoLoop 的双环思想组织工作：内环执行与修正，外环观察并独立检查是否满足目标；缺失和失败退回改进。选手决定目标和权限边界，并最终验收，不把 Agent 的“完成”声明当作完成证据。
5. **按场景组织协作。** 即时消息沿用 Rinx 界面，把安排或待办关联到原会话。软件工厂题可用 hagency 的任务分工与协作机制，观察每个 Agent 的进展、阻塞和交接；不要求其他应用接入工厂。
6. **比较改进前后的效果。** 让队外用户完成一次任务，记录不能完成或需要人工接管的地方。用明确反馈让 Agent 改善同一应用；有技术突破意愿的团队再说明生态反哺或 ROM 改进带来的任务价值。
7. **整理并交付。** 保留可运行版本、源码、来源与限制、截图、演示和验证记录。让 Agent 帮助整理材料，由选手核对真实性；正式答辩与备用视频使用 10/9 冻结版本。

9/26 两堂课以“意图 → AppCard → 真实数据与原生交互 → octoscode 协作修改 → 运行复核”为共同示例；讲清 Octos 在运行时的职责。9/27 的 Rinx 课堂以“打开文章编辑器 → 授权 → 编辑与预览 → 分享应用 → 接收者使用自己的账号 → 确认发送”为共同示例，再由选手设计新闻简报、邮件回复草稿或软件工厂验收等扩展。文章编辑器本身没有自动生成内容或自动读取聊天记录的 Agent；参赛作品需要补上自己的任务自动化并证明效果。每一步讲清输入、Agent 分工、人的判断和可观察结果。没有真实服务的练习必须说明使用示例数据，不把概念预览当作已经完成的集成。
