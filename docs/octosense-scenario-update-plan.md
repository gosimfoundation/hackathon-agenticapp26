# OctoSense 场景选题与进阶评奖：官网改版稿

2026-09-21。场景与评奖改版已发布；本次按 robrix2 作为主要开发基线继续更新。最新小程序范围见 [基线说明](robrix2-miniapps.md)。以下保留改版依据；奖项名额、对应奖金及兼得规则待最终细则，不采用未确认的分数权重。

本稿承接最新方向：本届大赛以 OctoSense 为核心，选题来自 OctoSense 官方应用指南；即时消息场景绑定 robrix2。先评价应用面向 Agent 自动化的能力，再评价服务于该应用的项目反哺与 OctoSense ROM 技术突破。

## 3. 官方 12 个场景与赛事练习

场景名称和指南链接来自 [OctoSense 官方应用指南](https://octosense.org/cn/#apps)。下列任务是赛事选题建议，不表示对应服务已经在参赛环境中实现；具体接入能力应以验证后的发布包为准。

| 场景 | 适合参赛的任务例子 | 应看到的任务结果 |
|---|---|---|
| [邮件](https://octosense.org/cn/apps/mail/) | 收到时间变更邮件，识别关联日程，提出更新和回复草稿 | 显示原邮件来源；确认后更新对应事件；后续来信更新同一任务 |
| [即时消息 · robrix2](https://octosense.org/cn/apps/messaging/) | 群聊约定聚会或项目交接，从讨论中整理时间、地点、待办和回复 | 卡片关联原消息；确认操作后回写状态；消息变化时更新原卡片 |
| [日历](https://octosense.org/cn/apps/calendar/) | 发现会议冲突，结合约束提出替代安排 | 区分建议、等待对方确认和已确认状态 |
| [天气](https://octosense.org/cn/apps/weather/) | 根据降雨、空气质量和活动计划提出出行调整 | 数据来源和更新时间可查；缺测显示未知；用户可决定是否改计划 |
| [新闻](https://octosense.org/cn/apps/news/) | 按关注主题准备有来源的晨间简报 | 内容可追溯；用户可控制主题、时间及是否播放 |
| [音乐](https://octosense.org/cn/apps/music/) | 为专注、通勤等具体情境组织播放任务 | 能执行播放、暂停、替换，并正确反馈当前状态 |
| [视频](https://octosense.org/cn/apps/video/) | 围绕一个问题和可用时间组织观看清单 | 用户能理解推荐依据、开始观看并调整计划 |
| [财经](https://octosense.org/cn/apps/markets/) | 把关注标的的公告和变化整理成研究卡 | 信息注明来源与时间，区分事实和分析；不要求交易执行 |
| [导航](https://octosense.org/cn/apps/navigation/) | 综合日历地点、出发时间和路况提出行动建议 | 确认目的地后开始导航；变化更新原任务，不擅自修改会议 |
| [购物与物流](https://octosense.org/cn/apps/shopping/) | 将订单、物流、安装与售后串成连续服务 | 后续事件更新同一订单任务，重要操作由用户确认 |
| [写作与创作](https://octosense.org/cn/apps/creation/) | 将素材和目标转为可迭代的内容任务 | 用户可修改约束、比较版本并确认最终内容 |
| [系统与设备](https://octosense.org/cn/apps/system/) | 检查存储、通知或设备状态，提出有范围的维护操作 | 先说明操作范围，获授权后执行并核验结果；可作为 ROM 进阶题 |

一个项目选择一个主要场景即可，也可联动其他场景。12 个场景共用评审，不拆成 12 组奖池。

统一最小交付应能展示：事件或意图输入 → Agent 理解并形成操作计划 → 用户查看或授权 → 执行 → 核验结果 → 状态变化或失败处理。仅生成界面、摘要或静态卡片，不足以证明完成了任务自动化。

## 4. 即时消息必须与 robrix2 绑定

页面专题标题建议为：

> 即时消息 × robrix2：以 robrix2 为起点，做能分享、能使用的小程序。

正文建议为：

> 以 robrix2 为消息与协作入口，保留熟悉的会话、消息和联系人界面。让 Agent 从对话中识别意图，将安排与待办整理成可操作的卡片或小程序；在用户授权后执行，并把结果带回原会话。

建议提供两个例题：

1. 日常协作：群聊聚会 → 时间与地点卡 → 冲突检查 → 确认回复或加入日历 → 后续变更更新原卡片。
2. 软件协作：hagency 任务事件 → robrix2 中的任务卡 → 查看阻塞与证据 → 用户验收或交接 → 结果返回工厂并回到原会话。

hagency 是软件协作题的数据与任务编排来源，不要求邮件、天气、音乐等所有作品都接入 hagency。既有软件工厂小程序方向继续保留，归入即时消息与协作专题。

本届主要开发基线已改为 OctoSense-org/robrix2 的 robrix2。现有机制包括 HTTP(S) 网页卡片和受限的原生 Octoscript 文章编辑器，接收者独立授权，草稿按账号隔离。历史 Agent2App 的任意脚本导入、版本回退与通用权限代理不能据此视为已经迁入；新增原生应用需要扩展宿主。

消息题的验收重点：来源会话与原消息可追溯；草稿和已发送状态清楚；发送对象可检查；消息修改、撤回或后续安排不会重复创建任务；权限拒绝和过期状态有反馈。单次授权不扩大为跨会话自动发言权限。

## 5. 进阶式评奖建议

### 最佳 Agentic 奖

核心问题：哪个应用最能让 Agent 帮用户完成真实任务？

页面采用定性评审维度：任务完成、可靠运行、人机协作，以复现证据说明效果。已撤下旧比例，不设置未确认的权重。

任务自动化应结合固定任务检查状态可读性、操作可执行性、多步骤完成和事件后续更新。重复运行要保留失败记录；人工步骤、成功次数和完成时间用于同一任务前后对照，不能直接把不同复杂度作品的点击数放在一起排名。

应用层作品可以获得最佳 Agentic 奖，不要求修改 ROM，也不要求提交与自身任务无关的 PR 或 issue。

### 最佳技术突破奖

在完成 Agentic 应用的基础上，评价项目反哺和 OctoSense ROM / 系统能力突破。所有达到基础要求的作品均可进入，不能限定为“先拿到最佳 Agentic 奖才能参加”。

进阶评审以可运行、可验证的 Agentic 应用为基础，再看生态贡献与 ROM / 系统集成效果。页面不设未经确认的分数门槛与附加分；具体评审细则另行公布。

生态贡献可以是可运行的应用接入、数据能力、组件、协议适配、测试与诊断；ROM 突破可以是系统事件触发、原生权限与系统桥、跨应用任务衔接等。都要展示它如何改善参赛应用，并提供版本、补丁、复现步骤和前后对照。同一成果不得在两个附加项重复计分。

单纯刷机成功、修改底层代码或累计 PR 数量，不自动构成技术突破。评审时尚未合并的 PR 可以按质量与复现证据评价，避免将维护者排期作为选手能否得分的条件。

### 奖金、名额与现场邀请需要一致定稿

已公开的奖池是人民币 ¥50,000，含现金与 MiniMax Token；现有名额是一等奖 1 名 ¥20,000、二等奖 2 名每名 ¥9,000、三等奖 3 名每名 ¥4,000。两类新奖项与这 6 个名额、金额的对应关系尚未决定，不能自行把两类奖改成无奖金荣誉，或把它们当成额外奖金。

建议一次性定稿两类奖的名额和金额、能否兼得，以及“前三名现场展示”的排序依据，再同步奖项卡、FAQ、晋级规则与宣传文案。期间不擅自改动已公开的人民币总额与分配，也不重新引入美元或换算过程。

线上初赛晋级 50 人、复赛完成评奖、10/17 前三名到 GOSIM 现场展示与颁奖的流程沿用；进阶评审不是增加第三轮比赛。现场不再改变线上评奖结果。
